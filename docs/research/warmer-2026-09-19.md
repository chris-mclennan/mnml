# The warmer — what a pane costs, before and after

2026-09-19.

The complaint this answers, in the user's words: *"we need some way of
speeding this stuff up, prefetching and spreading out and not
refreshing too often. cache data and poll intelligently to try and get
that big picture as its tickets, prs, and pipelines"* — and, because a
dozen Claude sessions share this machine's API allowance, *"maybe we
need a better 'load balancer'"*.

What went in: pacing with priority, one warmer per service across
processes, delta windows, conditional GETs, per-kind intervals, a
budget floor under which speculative work stops, and four new
request-log reasons so the REQUESTS pane shows the whole story rather
than only the part that cost something.

## How this was measured

Against the fakes — `mnml-fake-jira` and `mnml-fake-bitbucket` — at a
size that resembles a real workspace: `--extra-issues 13` on top of the
tracker fixture's twelve tickets, and `--extra-prs 20` on top of the
forge fixture's handful. Never against the live services.

The count is **what arrived on the server's wire**, off each fake's
`--log-file`, not what the client believes it sent. Each fake logs one
JSON line per request with its status, its response size, and — for
Jira, whose search puts its query in the POST body — the `jql` it was
asked for.

Each scenario is a headless `--dump` run of the real binary against a
scratch `MNML_DATA_ROOT` and its own ratelimit state file, so nothing
touches the machine's shared bucket and no other process's draws land
in the numbers.

`ms` is the whole process — start, config, auth, fetch, paint, exit —
on loopback. At these sizes it is dominated by process start and
should be read as an order of magnitude, not a benchmark.

The runs were driven by a throwaway shell script rather than anything
committed; the method above is the whole of it, and it is reproducible
from `zig-out/bin` with a scratch directory, the two fakes and the
`--dump --steps` scripts `snap listing` / `snap; key r; settle; snap`.

## The numbers

| scenario | service | requests | 304s | response bytes | ms |
| --- | --- | ---: | ---: | ---: | ---: |
| cold start | jira | 18 | — | 15,455 | 26 |
| warm start | jira | **2** | — | 10,567 | 22 |
| refresh, nothing changed | jira | 2 + **1** | — | +37 | — |
| refresh, 2 changed | jira | 2 + **1** | — | +693 | — |
| full refresh (`R`) | jira | 2 + **1** | — | +10,518 | — |
| cold start | bitbucket | 6 | 0 | 30,409 | 28 |
| warm start | bitbucket | 6 | **6** | **0** | 21 |
| refresh, nothing changed | bitbucket | 6 + **2** | 8 | **0** | — |
| refresh, 2 changed | bitbucket | 6 + 2 | 6 | 27,962 | — |
| full refresh (`R`) | bitbucket | 6 + 2 | 6 | 14,598 | — |

The `2 +` / `6 +` rows separate the startup chain from the keypress:
a `--dump` run has to open the pane before it can press anything, so
the refresh's own cost is the second number.

### Idle, no pane open

The statusline poller runs one `--values` per source per interval — 300 s
by both manifests — so ten minutes of an idle machine is two cycles per
service. What one cycle costs, measured as three consecutive `--values`
runs against a quiet fake (the cadence taken out, so the numbers do not
depend on where a 600 s window happens to fall):

| service | cycle | requests | 304s | response bytes |
| --- | --- | ---: | ---: | ---: |
| jira | first | 1 | — | 10,484 |
| jira | every one after | 1 | — | 10,484 |
| bitbucket | first | 9 | 0 | 14,712 |
| bitbucket | every one after | **1** | 1 | **0** |

So ten idle minutes costs Jira 2 requests and ~21 kB, and Bitbucket —
once the first cycle has filled the tag store — 2 requests and **no
bytes at all**.

Jira's poll is a `POST /rest/api/3/search/jql`, which has no
conditional form, so it pays the listing every time. That is the one
place left where a cheaper idle is available and was not taken.

A wall-clock run of the real cadence was also done twice (600 s, both
services, nothing else on the machine) and agreed: 1-2 Jira requests
and 11-22 Bitbucket requests, the spread being whether the window
caught one cycle or two.

## What each number is

**Jira cold 18 → warm 2.** The cold start is `/myself`, the search,
and one dev-status call per unresolved ticket on the tree. On the
second run every one of those dev-status answers is already held under
the ticket's own `updated` stamp, so a ticket that has not moved costs
nothing at all: the pane pays for `/myself` and the listing, and
paints the rest from the store. This is the mechanism that was already
on `main`; the measurement is here because it is the baseline the rest
is measured against.

**The Jira delta is about bytes, not requests.** A refresh was one
request before and is one request now. What changed is what comes back:
37 bytes for "nothing moved", 693 bytes for "two tickets moved",
against 10,518 bytes for the listing again. On a rate-limited API the
token is the scarce thing and the delta does not save one — but on a
slow connection, and on the user's attention, a 37-byte answer lands
in a different order of time from a 10 kB one. `R` is the 10 kB
version, deliberately, because a window can never notice a ticket that
has dropped OUT of the query.

**The Bitbucket warm start is six 304s and no bytes.** Every GET that
has the server's `ETag` in hand goes out carrying `If-None-Match`; the
server answers `304 Not Modified` with no body and the client hands
back the body it already held, so the caller cannot tell. Six round
trips, six tokens, zero bytes. This is the single largest change in the
table: 30 kB became 0.

**Bitbucket's cold start is the tab on screen, not every tab.** The
pane used to fetch all three configured tabs before its first paint.
Only the one on screen is a `pane_open` now; the rest go out as
`warm`, a priority that steps aside for anything a reader does — and
only when this process holds the machine's warm lock, so a second pane
reads what the first left behind. The before-and-after of that change
was not measured as a pair (the eager path is gone); what is measured
is the unit test that counts one `pane_open` job and two `warm` ones,
and none of the two when the lock is held elsewhere.

**`refresh, 2 changed` costs the listing.** Two pull requests moving
moves the listing's bytes, so its tag moves and the listing comes back
whole. That is correct and not improvable without a server-side delta
Bitbucket does not offer; the win is the far commoner case above it.

**The measurement found a bug worth more than the measurement.**
`Store.save` wrote its JSON file with `std.zig.fmtString`, which
escapes for a Zig string literal — so a response carrying an
apostrophe or a control byte produced an escape no JSON parser will
read, and the next run's `Store.open` silently handed back an empty
cache. The module's own promise is that a cache it cannot read costs
requests rather than correctness; it was keeping that promise
perfectly, every run, and nothing said so. It surfaced as "why does
the second Bitbucket poll of two never send `If-None-Match`". Fixed,
with a round-trip test over a body that actually contains those bytes.

## Decisions taken along the way

**Pacing holds background work and never holds a reader.** The obvious
reading of "space requests at one per `1/rate + margin`" is to hold
every request. Measured, that adds a full gap (3.5 s for Jira, 5.2 s
for Bitbucket) to the second request of a pane open, for no tokens
saved — the bucket already bounds how fast a person can spend. So
`Gate.hold` returns the wait for background work and zero for
interactive work. The interactive request still *reserves* its slot, so
background work steps behind it exactly as if it had waited. Spacing
protects the bucket from bursts; it was never meant to protect it from
people.

**Only `r` and the interval ask for a window.** The corpus caught two
ways a delta answers the wrong thing. A picker that rewrites the
query: the window was measured against a question nobody is asking any
more, so the query is now part of the sync mark and a changed question
falls back to a full refetch. And a write this pane just made:
reassign a ticket away from yourself and the Assigned tab has to lose
it, but a window can only ever see rows that moved WITHIN the query,
never one that dropped out of it. So everything except `r` and the
interval — every post-write and post-picker path — asks for the whole
listing. A full refetch is merely dearer; a window over a changed row
set is wrong.

**The Jira delta merges generations rather than re-sorting.** A delta
returns what moved, and Jira's `Issue` carries a `std.json.Value` that
cannot be moved between arenas without a deep clone. Rather than clone,
each delta keeps its own arena as a generation under the merged slice
and the base arena is freed only by a full refetch. Capped at eight
generations, past which a refetch is full whatever was asked for — an
unbounded chain is a leak with a nicer name, and something has to
notice a ticket that dropped out eventually.

**Bitbucket gets conditional GETs instead of a client-side delta.**
Bitbucket's tab data is a union of four shapes (flat list, repo tree,
pipelines tree, branches), each rebuilt wholesale on a refetch. A
merge would need the generations machinery four times over. The `ETag`
round trip gets the same "nothing moved" case to zero bytes with no
merge at all, and the server does the comparison. A `updated_on >`
BBQL window is still what the statusline chip's query uses
(`chip_stale_after_days`), which is where it earns its keep.

**A `cache_hit` line carries no status.** The REQUESTS pane counts
requests by counting lines; a cache hit that carried `200` would
inflate every count in the pane. It carries `status: null`,
`wait_ms: 0` and `tokens_after: 0` instead, so the line shows the
answer without claiming the cost.

**The one-warmer lock heartbeats rather than timestamps its start.**
A warm sweep of a big workspace is paced, and pacing is slow on
purpose, so "started more than N seconds ago" is not evidence of
death. The holder rewrites `ts` as it works; a lock nobody has touched
for five minutes is taken whatever its pid says, which is also what
covers a reused pid and a platform with no liveness probe.

## What is not covered

* **The live services.** Nothing here touched Atlassian. Bitbucket
  Cloud's REST API documents `ETag` / `If-None-Match` on its read
  routes and Jira Cloud does not document it on `/rest/api/3/search/jql`
  (a POST), which is why the conditional path is Bitbucket-only. That
  is a reading of the documentation, not a measurement: the first
  person to run this against the real API should check the response
  headers on a listing before trusting the saving.
* **A 429 under pacing.** The gate is measured on a fake that never
  throttles. The bucket's own penalty path is unchanged and still
  covered by its own tests.
* **Many processes at once.** The lock is tested with two `Lock`
  values in one process against one file. Two real binaries racing for
  it has not been run.
