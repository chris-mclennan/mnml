## What is still worth a track

Memory after a few edits on a 100 MB source file is 2.4 GB, five times
the file; on the log it is 1.4×. The difference is the parse tree and
the undo snapshots a highlighted buffer carries. The Rust app sits at
3.3 GB on the same file, so this is not a regression, but a 100 MB
source file is a thing people open by accident, and the number should
come down before it is noticed.

## After the memory track

`-Dmem-report` counts every byte live through the app's allocator and
every byte live inside the tree-sitter runtime (its own malloc, routed
through `ts_set_allocator`), and prints both — plus each document's
parts and, now, the parse-job tally — as a headless session ends. The
numbers below are that build on the 100 MB `.rs` cell, one process per
stopping point, `ps` RSS at each step.

### Where the 2.4 GB was

| after | RSS | app live | tree-sitter live |
|---|---|---|---|
| open (+1 s) | 1402 | 224 | 632 |
| insert top | 1476 | 274 | 680 |
| goto end | 1606 | 281 | 734 |
| insert end | 2179 | 384 | 1109 |
| goto top | 2219 | 384 | 1142 |
| page down | 2148 | 384 | 1095 |
| undo | 2380 | 384 | 1236 |
| search | 2963 | 384 | 1714 |
| search, then 15 s idle | 2319 | 199 | 2567 |

The steps are not where the memory goes — the parse is. The counter
climbs through the idle because the first parse of 100 MB takes about
seven seconds and the second one is still running when the keys are
done; the tally says two jobs started, two posted, two results adopted, none
dropped, and the one tree that was replaced disposed of — so at the end
exactly ONE tree is held and nothing leaked. **One tree-sitter tree over 100 MB of Rust is 2.5 GB** —
about 25× the source. That is the finding: not the undo stack (delta
entries, 0 KB across the whole run), not the search (`/QJZ` has two
matches), not the line index (22 MB), not the frame arena.

Switching the two suspects off one at a time, same cell, same build
(RSS here reads a little higher than the plain build's — the counting
wrapper is in the path and the last row waits 15 s for the second parse
to land):

| | RSS after | RSS settled | app peak | tree-sitter live |
|---|---|---|---|---|
| as shipped then | 2946 | 2319 | 834 | 2567 |
| highlighting gated at 4 MiB | 798 | 893 | 672 | 0 |
| no language server | 2208 | 3765 | 409 | 2567 |
| both | 446 | 446 | 309 | 0 |

The second owner is the language server. `rust-analyzer` is on this
machine's PATH, so a `.rs` buffer attaches one: `lsp.zig`'s `attach`
JSON-encodes the whole 100 MB on `didOpen`, `syncPane` re-encodes the
whole 100 MB whenever a burst holds more than one splice (three typed
characters in a frame), and two of the server's answers came back at
75 MB and 196 MB to parse. That is the ~350 MB between the third row and
the fourth. It is untouched by this track — see "Left standing" below.

The floor, with neither, is 446 MB for a 100 MB file: the text (100, and
150 of capacity before this track), the line index (22), the 150 MB the
file read grows through, and what the allocator holds on to rather than
returning.

### What changed

`editor.highlight_max_bytes` already existed — the gate, the statusline
chip, the toast, the per-buffer override and their tests all shipped
with it — and its default was 0, no limit. The Rust app has the same
ceiling hard-coded at 4 MiB (`src/buffer.rs`, `HIGHLIGHT_BYTE_LIMIT`),
silently. mnml-zig's default is now the same 4 MiB, and it says so when
it applies.

Same three cells, one round each, both binaries built ReleaseSafe on
this machine back to back (`~/Projects/mnml-zig-bench/results.jsonl`,
rows commented `# bigfile-memory`):

| file | RSS open | RSS after the edits | CPU s |
|---|---|---|---|
| 10 MB .rs | 42 → 42 | **385 → 95** | 0.7 → 0.3 |
| 100 MB .rs | 446 → 446 | **2377 → 605** | 4.5 → 1.8 |
| 100 MB .log | 140 → 140 | 253 → 253 | 0.9 → 0.9 |

No step is slower; every timing is inside the run-to-run noise the
first table already shows (100 MB .rs: open 0.39 → 0.40, insert end
0.53 → 0.51, search 0.79 → 0.77). `.log` is unchanged because a log
file has no grammar and never had a tree. Opening is unchanged because
the parse never happened on the opening frame anyway — it is the idle
gate that no longer starts one.

The whole of the 100 MB .rs difference is the ceiling and nothing else:
the OLD binary, given `.editor.highlight_max_bytes = 4194304` in a
config file, lands on 606 and 605 MB over two rounds — the same as the
new default's 605.

### Left standing, measured

- **The language server on a very large buffer, ~350 MB.** `attach`
  (`src/app/lsp.zig`) JSON-encodes the whole text on `didOpen`, and
  `syncPane` re-encodes the whole text whenever a burst carries more
  than one splice — which three typed characters in one frame already
  do, even though every splice in the burst carries the pre-edit points
  `didChange` wants. Two of rust-analyzer's own replies came back at
  75 MB and 196 MB to parse (`src/rpc/jsonrpc.zig`'s `create`). The two
  candidate fixes are a size ceiling of its own, in the shape the
  highlighter's now has, and sending the burst as N range edits instead
  of the full text.
- **The buffer's capacity, ~50 MB of address space and none of it
  resident.** Typing one character into a 100 MB document makes its
  `ArrayList` ask for 1.5× — 150 MB of capacity for 100 MB of text. A
  reserve that asks for what it needs plus a megabyte was written,
  tested and measured: RSS 606 → 605, i.e. nothing, because the extra
  50 MB is never written to and so is never resident. It was dropped
  rather than shipped — it would have traded an unmeasurable saving for
  a 50× increase in reallocation frequency on a document that grows in
  small steps.
- **One frame's arena reaches ~100 MB on a 100 MB file** (chunk
  allocations of 50, 72 and 97 MB charged to `editor_view.draw`, which
  is where the arena happened to run out rather than who filled it).
  The arena is reset per frame and retains only 8 MB, so this is a
  within-frame cost, not a leak. Not attributed further.

### Three things that were not the problem

The 2026-09-21 note guessed the parse tree and "the undo snapshots a
highlighted buffer carries". Half right. Across the whole 100 MB run
the undo and redo stacks hold **0 KB** — the delta representation that
landed in `d05f4033` works — the search builds two matches, and the
line index is 22 MB. Nothing was leaking either: the tally shows every
tree that was replaced was freed.
